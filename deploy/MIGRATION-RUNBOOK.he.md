# נוהל העברת נתונים — מ-Vercel/Supabase לתשתית גלעם

מטרה: להעביר את **כל הנתונים** מבסיס הנתונים הנוכחי (Supabase) לבסיס הנתונים החדש בשרת גלעם,
עם בדיקת שלמות, גיבוי לפני המעבר, ותוכנית חזרה. **לא** משביתים את המערכת הקיימת עד שהחדשה אושרה.

> עיקרון: המעבר הוא מעבר **נתונים + כתובת**, לא רק החלפת URL. כל עוד לא הועברו הנתונים —
> המערכת החדשה ריקה.

## דרישות מקדימות
- המחסנית החדשה רצה (ראו `README.md`), והסכימה נטענה (`deploy/schema.sql`).
- מחרוזת חיבור ישירה ל-Supabase (Dashboard → Project Settings → Database → Connection string,
  תפקיד `postgres`, פורט 5432 הישיר — **לא** ה-pooler, כי `pg_dump` צריך חיבור ישיר).
- `pg_dump`/`pg_restore`/`psql` גרסה 16 על מכונת המעבר.

## שלב 0 — גיבוי לפני הכול (שני צדדים)
```bash
# גיבוי מקור (Supabase) — רשת ביטחון
DATABASE_URL="$SOURCE_DB_URL" deploy/scripts/backup.sh /var/backups/pre-migration
# אם היעד כבר מכיל משהו — גבה גם אותו
DATABASE_URL="$TARGET_DB_URL" deploy/scripts/backup.sh /var/backups/pre-migration
```

## שלב 1 — ספירת מקור (בסיס להשוואה)
```bash
DATABASE_URL="$SOURCE_DB_URL" deploy/scripts/verify-integrity.sh | tee source-counts.csv
```

## שלב 2 — העברה בפועל
```bash
SOURCE_DB_URL="postgres://postgres:***@db.<ref>.supabase.co:5432/postgres" \
TARGET_DB_URL="postgres://postgres:***@localhost:5432/galam" \
  deploy/scripts/migrate-from-supabase.sh
```
הסקריפט: שולף **data-only** מ-11 הטבלאות, טוען ליעד עם `--disable-triggers`, מיישר את
רצף מספרי הכרטיסים (`calls_num_seq`) לפי המקסימום שהועבר, ומדפיס ספירות של שני הצדדים +
**diff**. יציאה 0 = הספירות זהות; יציאה 2 = יש פער לבדיקה.

## שלב 3 — בדיקת שלמות
- ה-diff בסוף שלב 2 חייב להיות ריק (ספירות שורות זהות בכל 11 הטבלאות).
- בדיקה נקודתית מומלצת: השוו את מספר הקריאה הגבוה ביותר, ואת סך `records`:
  ```bash
  psql "$TARGET_DB_URL" -c "select max(num) from calls; select count(*) from records;"
  ```
- העברת 2–3 רשומות ידניות לדגימה (שם מחלקה, קריאה אחרונה) ובדקו שהן זהות למקור.

## שלב 4 — הפניית האפליקציה החדשה
ב-`config.js` של הפריסה החדשה הגדירו את `SUPA_URL`/`SUPA_KEY` כך שיצביעו על היעד
(Option A: ה-origin של האפליקציה; Option B: כתובת ה-Supabase העצמית + מפתח anon).
בשלב זה **שתי המערכות חיות במקביל** — הקיימת ב-Vercel עדיין פעילה.

## שלב 5 — בדיקות קבלה על המערכת החדשה (לפני ניתוק הישנה)
ראו צ'קליסט מלא ב-`IT-HANDOFF.he.md`. לכל הפחות: פתיחת קריאה בטופס → הופעה בניהול →
עדכון סטטוס → רענון דף (הנתון נשמר) → ייצוא אקסל → גיבוי/שחזור.

## שלב 6 — Cutover (בתיאום IT)
1. "הקפאת כתיבה" קצרה: הודעה למשתמשים לא לפתוח קריאות חדשות ל-10–15 דקות.
2. העברת דלתא: הריצו שוב את שלב 2 (הסקריפט מוסיף; כדי למנוע כפילויות על רשומות שכבר
   הועברו, עדיף במעבר הסופי להריץ על יעד **ריק** שנטען מחדש מהסכימה — ראו הערה למטה).
3. הפניית ה-DNS הארגוני לכתובת החדשה; השארת Vercel פעיל כ-fallback.
4. בדיקת עשן על הכתובת הארגונית.

> **הערה על כפילויות:** המפתחות הראשיים הם טקסטואליים ויציבים (`id`/`num`/`serial`/`name`),
> כך שטעינה חוזרת של אותן רשומות תיכשל על PK (לא תיצור כפילויות) — אבל המעבר הסופי הנקי
> הוא: אתחל יעד ריק (`schema.sql`), הרץ שלב 2 פעם אחת סופית אחרי הקפאת הכתיבה.

## תוכנית חזרה (Rollback)
- המערכת הישנה (Vercel + Supabase) **לא נגעו בה** ולא נמחקה — חזרה = להחזיר את ה-DNS
  לכתובת Vercel. זמן חזרה: דקות.
- אם התגלתה בעיית נתונים ביעד: שחזרו מהגיבוי של שלב 0 (`deploy/scripts/restore.sh`).
- אין למחוק את פרויקט ה-Supabase ואת אתר ה-Vercel עד שבוע לפחות של עבודה יציבה על החדש.

## לאחר ייצוב (ניקיון, בתיאום IT)
- החלפת/ביטול מפתחות ה-anon של פרויקט ה-Supabase הישן.
- הורדת אתר ה-Vercel או השארתו כ-staging בלבד.
